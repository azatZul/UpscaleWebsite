# Перенос face-гейта: результат первого этапа

## Статус

Численный модуль перенесён, но **гейт не встроен в рабочую обработку**.
Проверка Canvas на этом наборе проходит по уточнённой методике
(leave-one-photo-out, см. ниже), но методика выбрана после просмотра этих же
данных. Поэтому перед интеграцией её нужно подтвердить на новых фотографиях.
Публикации не было; worker, выбор лиц, тексты и аналитика остались прежними.

Политика `face-guard-v1-web-pixel` сохраняет проверки деталей, SSIM и минимального
межглазного расстояния из Swift. Смещение ориентиров она явно не использует
(`landmarks: false`). Полная `face-guard-v1` сохранена как эталонная политика для тестов.
`pass` не является гарантией улучшения или сохранения личности.

## Что проверено

- В `tests/fixtures/face-quality/ios-reference/` лежат политика, 26 эталонных оценок
  и manifest с SHA-256, ревизиями и моделями. Swift-исходники в сайт не копируются:
  manifest хранит их хеши по путям в iOS-репозитории (`iosSources`). На момент
  проверки хеши `FaceRestorationQualityGate.swift` и `QualityGateProbe.swift`
  совпадают с рабочей копией iOS-проекта. Исходные репозитории не изменялись.
- На 26 одинаковых Float32-парах решения JS совпали с зафиксированным Swift.
  Максимальные абсолютные ошибки: sourceSignal `0.00000271`, retention `0.00000074`,
  SSIM `0.00000058`, native sourceSignal `0.00000259`, native retention `0.00003898`.
  Допуск каждой метрики — `0.003`. Ошибки уменьшились после того, как сумма ядра Гаусса
  стала накапливаться во Float32, как в Swift.
- Проверены обе политики, равенства на порогах, слабый сигнал, недоступные native
  данные, нечисловые значения, неизменённая текстура, сглаживание с добавленным шумом,
  gamma-encoded luma и half-pixel bicubic.
- `npm run test:tool`: 138 тестов пройдены.

## Полный путь Core Image / Canvas

Подготовлены 150 случаев на движок: 25 лиц из 12 фотографий, исходный масштаб и
кропы около 600/800/1024/1400/2000 пикселей. `big-1-actual` не смешивается с выходами
GFPGAN: он присутствует только в численной сверке исходных 26 пар.

Все варианты одной фотографии зависимы. Увеличенные исходники отмечены отдельно;
масштабирование не создаёт настоящие детали. Выход GFPGAN в этом эксперименте
фиксирован: модель не запускалась заново на каждом масштабе. Оригинал ограничен
областью лица с запасом, чтобы увеличение маленького лица не создавало гигантскую
полноразмерную фотографию. В Core Image и браузеры передаётся один и тот же
нормализованный sRGB PNG, transform и результат модели. Это изолирует ресемплинг;
прямой путь декодирования исходных JPEG пока не проверен.

Численные метрики на выходах Core Image и Canvas считает один и тот же проверенный
JS-модуль. Изображения и большие Float32-буферы остаются в игнорируемой папке.
Обезличенный численный отчёт: `benchmarks/browser/2026-11-11/face-quality-canvas.json`
(Chromium 156.0.8078.4, WebKit 26.5).

### Сглаживание Canvas

После изменения размера canvas сбрасывает состояние контекста, поэтому
`imageSmoothingQuality` теперь задаётся явно сразу после resize (`--smoothing`).
Сравнение на тех же 150 случаях:

| Сглаживание | Устойчивые pass (Chromium / WebKit) | Устойчивые skip | Пограничные расхождения |
| --- | ---: | ---: | ---: |
| `low` (по умолчанию) | 74 / 96 | 27 / 19 | 7 |
| `medium` | 70 / 91 | 20 / 14 | 8 |
| `high` | 68 / 95 | 18 / 16 | 6 |

`low` ближе всего к Core Image: у Chromium ошибки canonical-метрик на крупных кропах
при `medium`/`high` растут в несколько раз. WebKit от настройки почти не зависит.
Отчёт сохранён с `low`.

### Оценка погрешности

Погрешность оценивается отдельно для каждого браузера и диапазона кропа
(≤512: 22 случая, 512–1024: 76, >1024: 52 на движок). Вызывающий код знает cropPixels,
а ресемплинг вверх и вниз ведёт себя по-разному. Native-ошибки учитываются только
при crop >512. Ошибка retention учитывается только там, где сила сигнала хотя бы
в одной реализации активирует соответствующую ветку.

Для каждой строки граница считается **без всех вариантов той же фотографии**
(leave-one-photo-out). В прежней версии строка сама расширяла свой интервал.
Тогда любое расхождение попадало в интервал по построению, и условие
«0 устойчивых расхождений» выполнялось автоматически. Решение устойчиво, если оно
не меняется во всех углах интервала ±2 погрешности. Если native-ветка может
активироваться, запас native retention <0.02 дополнительно делает случай пограничным.

Максимальные расхождения по группам (sourceSignal / retention / SSIM /
native sourceSignal / native retention):

| Движок, кроп | Максимальные абсолютные разницы |
| --- | --- |
| Chromium ≤512 | 0.0086 / 0.0154 / 0.0128 / — / — |
| Chromium 512–1024 | 0.0032 / 0.0146 / 0.0255 / 0.0012 / 0.0081 |
| Chromium >1024 | 0.1058 / 0.0252 / 0.0253 / 0.0012 / 0.0073 |
| WebKit ≤512 | 0.3874 / 0.3121 / 0.0039 / — / — |
| WebKit 512–1024 | 0.0346 / 0.0147 / 0.0009 / 0.0886 / 0.0438 |
| WebKit >1024 | 0.1084 / 0.0283 / 0.0013 / 0.0263 / 0.0088 |

Результат: **0 устойчивых расхождений**, 7 пограничных (шесть в Chromium, одно
в WebKit). Устойчивых pass 74 в Chromium и 96 в WebKit, устойчивых skip 27 и 19.
`passed: true`. По прежней методике (один глобальный интервал на все случаи) на тех
же измерениях было 0 устойчивых pass и `passed: false`.

Все 7 расхождений заранее отмечены как пограничные по погрешностям **других** фотографий:

- Chromium, `wedding-4`, пять увеличенных масштабов: SSIM у порога 0.88
  (запас 0.008 при погрешности до 0.026), pass → geometry-risk.
- Chromium, `girls-after-2`, crop 800: native retention у порога 0.65; причина
  меняется с native-detail-loss на correlated-detail-loss, сам отказ сохраняется.
- WebKit, исходный `wedding-2`, crop 193: pass → correlated-detail-loss.
  У WebKit в диапазоне ≤512 самые большие расхождения sourceSignal/retention.

## Следующая отдельная доработка

1. Зафиксировать текущую методику (группы по браузеру и кропу, leave-one-photo-out,
   ±2 погрешности, `low`) и проверить её на **новых** фотографиях без подстройки.
   Не менять пороги качества для компенсации разных фильтров.
2. Разобрать WebKit на кропах ≤512 (ресемплинг вверх) и SSIM Chromium на
   увеличенных исходниках. Если настройки Canvas не обеспечат воспроизводимость,
   выделить общий детерминированный affine-ресемплер для canonical/native кропов.
3. После успешной приёмки вернуться к worker, раздельным patch/defaultSelected,
   ручному выбору, текстам и агрегатной аналитике по согласованному плану.

Сравнение центров глаз и границ 8/24, полная проверка прозрачности, интеграционные
сценарии и замеры нового гейта на физическом iPhone **отложены**, поскольку гейт
не подключён к продукту. iPhone-сессия была создана, но обработка на телефоне
не запускалась; сессия закрыта. Chrome на физическом iPhone не проверен.

## Воспроизведение

```sh
node scripts/check_face_quality_parity.mjs ../Upscaler/build/face-quality-lab-v2/swift-verification
xcrun swiftc -O -parse-as-library -module-cache-path .web-model-work/swift-cache scripts/prepare_face_quality_canvas.swift -o .web-model-work/prepare-face-canvas
.web-model-work/prepare-face-canvas ../Upscaler/build/face-quality-lab-v2 .web-model-work/face-quality-canvas
node scripts/check_face_quality_canvas.mjs .web-model-work/face-quality-canvas .web-model-work/face-quality-canvas/report.json --smoothing=low
node scripts/render_face_quality_report.mjs .web-model-work/face-quality-canvas
```

Скрипты не зависят от текущей директории. Для браузерного скрипта доступны
`USCALE_PLAYWRIGHT_MODULE` (проверено с Playwright 1.62.1),
`PLAYWRIGHT_BROWSERS_PATH` и `USCALE_CHROMIUM_EXECUTABLE`. Core Image/Vision и
тестовым браузерам может потребоваться доступ к системным сервисам macOS.
`--summarize` пересчитывает только приёмку по уже сохранённым измерениям и
сохраняет их provenance.

Локальное интерактивное сравнение: `.web-model-work/face-quality-canvas/index.html`.
Оно содержит приватные изображения и не предназначено для публикации.
