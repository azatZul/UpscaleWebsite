# Upscale result sharing: developer handover

This is the implementation and production handover for the internal computer-side command that runs an AuraLens image flow and creates a temporary before/after page on `upscales.app`. It is developer tooling, not an end-user upload product.

## Change set

- Website and command: [UpscaleWebsite PR #2](https://github.com/azatZul/UpscaleWebsite/pull/2)
- API and result storage: [auralens-server PR #3](https://github.com/AlexandrGraschenkov/auralens-server/pull/3)

Both PRs must be deployed for production use. Deploy the backend first and the website second.

## What was built

The website PR contains:

- `scripts/upscale_result/upscale_result.py`, the internal command-line tool;
- support for Creative Upscale and Photo Restoration;
- a responsive result page at `/results/<result UUID>` with before/after comparison and result download;
- local mocked end-to-end tests and the static-site build integration.

The backend PR contains:

- developer-only Creative Upscale and Photo Restoration routes;
- a no-cost authentication preflight route that is called before source download;
- a protected endpoint that publishes before/after media;
- local and Google Cloud Storage result backends;
- public-by-link metadata, media, and download routes;
- exact logical expiry after 3 or 7 days;
- a Google Cloud Storage access check during service startup.

Creative Upscale sends the entire image in one provider request (`tile_count: 1`). It does not make one paid request per tile or fall back to a second provider. Photo Restoration sends one Replicate request.

## How it works

1. A developer runs the command with an HTTPS image URL, a flow, and a 3- or 7-day lifetime.
2. Before fetching the source image, the command calls `GET /internal/v1/tool-access` with the developer bearer key. A failed check stops the command without downloading the source or contacting a paid provider.
3. After authentication succeeds, the command downloads and validates the source image.
4. AuraLens sends one whole-image request to WaveSpeed for Creative Upscale, or one request to Replicate for Photo Restoration.
5. The command downloads the provider output and uploads the source and result together to `POST /internal/v1/results`.
6. AuraLens creates a new UUID, stores both images and a manifest in the private bucket, and returns `https://upscales.app/results/<UUID>`.
7. The result page uses that UUID to load metadata from AuraLens. In the current implementation, AuraLens reads the private bucket objects and streams the before image, after image, or download to the browser.
8. Once the manifest's expiry timestamp is reached, the public endpoints reject access. Google Cloud Storage lifecycle rules remove the underlying objects asynchronously.

The UUID in the website URL is the result UUID generated by AuraLens when the pair is published. It is not the provider prediction ID and it is not the command's idempotency key. The object layout is:

```text
results/3d/<result UUID>/before.<extension>
results/3d/<result UUID>/after.<extension>
results/3d/<result UUID>/manifest.json

results/7d/<result UUID>/before.<extension>
results/7d/<result UUID>/after.<extension>
results/7d/<result UUID>/manifest.json

idempotency/<SHA-256 of command idempotency key>.json
```

The bucket does not need to be public and the website does not contain Google credentials. Serving media through AuraLens also means that Cloud Storage CORS configuration and a storage CDN are not required for the first production release.

### Result endpoints and what `410` means

There is no timer or separate expiry job that produces `410`. The result page calls these existing backend endpoints:

- `GET /public/v1/results/<UUID>` returns the manifest metadata and media URLs;
- `GET /public/v1/results/<UUID>/media/before` returns the source image;
- `GET /public/v1/results/<UUID>/media/after` returns the processed image;
- `GET /public/v1/results/<UUID>/download` downloads the processed image.

Each endpoint reads the manifest and compares `expires_at` with the current server time. While an expired manifest still exists, it returns HTTP `410 Gone`. After the asynchronous storage lifecycle has physically deleted the manifest, the same request returns `404 Not Found`. In both cases the result is no longer accessible. The result page treats `410` as the explicit expired state.

### Should media use signed URLs?

The current PR does not use Google Cloud Storage signed URLs for reads; it streams both preview and download bytes through AuraLens. Short-lived signed URLs are a good next production optimization because they move large-image delivery out of Cloud Run while keeping the bucket private.

The recommended read design is not one fixed URL created for the entire 3- or 7-day lifetime. Instead, `GET /public/v1/results/<UUID>` should first enforce the manifest expiry and then return signed `GET` URLs valid for a short window, such as 15 minutes, capped at the remaining result lifetime. On each page load, active results receive fresh URLs. This preserves the stable website URL, reduces Cloud Run memory and bandwidth, and limits the useful lifetime of a leaked storage URL. Google V4 signed URLs can be valid for at most seven days, and anyone possessing one can use it until it expires or its signing key is rotated. See [Google Cloud Storage signed URLs](https://cloud.google.com/storage/docs/access-control/signed-urls).

Generating signed URLs from Cloud Run also requires the runtime identity to have `iam.serviceAccounts.signBlob`, commonly via `roles/iam.serviceAccountTokenCreator` on the signing service account. This is additional IAM surface and must be granted narrowly. See [Google's signed-URL helper requirements](https://cloud.google.com/storage/docs/access-control/signing-urls-with-helpers).

Signed upload URLs are a separate improvement and are the preferred solution to the combined request-size issue documented below. The developer bearer key must still be checked first; after that, AuraLens can issue short-lived upload targets and finalize the result only after validating the uploaded objects.

## Endpoint security

Every endpoint that can spend provider money or publish data is under `/internal/v1/` and requires:

```http
Authorization: Bearer <UPSCALER_TOOL_API_KEY>
```

The protection works as follows:

- The command first calls the protected, no-cost `GET /internal/v1/tool-access` endpoint. A failed authentication check prevents source download and provider submission.
- AuraLens refuses to enable the tool API when `UPSCALER_TOOL_API_KEY` is missing or shorter than 32 characters. It returns HTTP `503`, so a deployment cannot accidentally expose an unprotected paid endpoint.
- A missing or incorrect bearer key returns HTTP `401`.
- The server compares keys with a constant-time comparison.
- The key is independent of the mobile app's HMAC credentials. It is only for trusted developers running this command.
- The server copy belongs in Google Secret Manager and is exposed only to the Cloud Run service as an environment variable.
- A developer copy belongs only in the website repository's ignored `.env` file. `.env` and `.env.*` are ignored; only `.env.example` is tracked. Confirm with `git check-ignore .env` before adding files to a commit.
- The private bucket grants object access only to the Cloud Run runtime service account. Do not create public object URLs or place a service-account key file in either repository.

The `/public/v1/results/<UUID>` routes intentionally do not use the developer key. A result link is public-by-link: possession of its random UUID grants read access until expiry. The UUID is unguessable in normal use, but it is a sharing capability rather than user authentication. Do not use this design for private account data.

A static bearer key prevents unknown callers from reaching paid routes, but it is not a complete abuse-control system. Keep the key within the small developer group, rotate it after suspected disclosure, monitor provider spend, and add per-key quotas or rate limiting if the tool's operator set grows. The current server accepts one key, so rotation is coordinated: add a new secret version, deploy it, update developer `.env` files, and then stop using the old value.

## Run the command

Install the command-only dependencies:

```sh
python3 -m pip install -r scripts/upscale_result/requirements.txt
cp .env.example .env
```

Set the real values in `.env`:

```dotenv
UPSCALER_TOOL_API_KEY=<same value attached to AuraLens in Secret Manager>
AURALENS_API_BASE_URL=https://auralens-406817559814.us-central1.run.app
```

Creative Upscale is the default flow:

```sh
python3 scripts/upscale_result/upscale_result.py \
  'https://example.com/photo.jpg' \
  --creativity 0 \
  --resolution 4k \
  --retention 7
```

Creative Upscale supports `--creativity -2..2` and `--resolution 2k|4k|8k`.

Photo Restoration:

```sh
python3 scripts/upscale_result/upscale_result.py \
  'https://example.com/old-photo.jpg' \
  --flow photo-restoration \
  --output-format jpg \
  --safety-tolerance 2 \
  --seed 42 \
  --retention 7
```

Photo Restoration supports `--output-format jpg|png|webp`, `--safety-tolerance 0|1|2` (`0` is strictest), and an optional integer `--seed`. Omit `--seed` for a provider-selected seed.

HTTP image URLs are rejected by default. `--allow-http` is only for a local backend and local test images.

## Production setup

The commands below assume the backend PR has been checked out in `auralens-server`. Run them from that repository so the lifecycle-file path resolves correctly.

### 1. Obtain the required Google Cloud access

The current local Google account could not read the `auralens-472014` Cloud Run service during development, so an AuraLens project administrator must grant access or perform the setup. Do not continue by creating a bucket in a different project unless that is an intentional architecture decision.

The person provisioning the release needs permission to inspect/update Cloud Run, create/configure a bucket, create/grant access to a secret, and act as the runtime service account. Google documents the relevant controls in [Cloud Run deployment permissions](https://cloud.google.com/run/docs/deploying), [Cloud Storage IAM roles](https://cloud.google.com/storage/docs/access-control/iam-roles), [Secret Manager access control](https://cloud.google.com/secret-manager/docs/access-control), and [service-account user permissions](https://cloud.google.com/iam/docs/service-account-permissions#iam-serviceAccountUser).

Use project-scoped variables for the remaining commands:

```sh
export RESULT_PROJECT_ID='auralens-472014'
export RESULT_REGION='us-central1'
export RESULT_SERVICE='auralens'
export RESULT_BUCKET='<globally-unique-private-bucket-name>'
```

Enable the required services if they are not already enabled:

```sh
gcloud services enable \
  run.googleapis.com \
  storage.googleapis.com \
  secretmanager.googleapis.com \
  artifactregistry.googleapis.com \
  --project="${RESULT_PROJECT_ID}"
```

### 2. Identify the Cloud Run runtime identity

Inspect the service before granting access:

```sh
gcloud run services describe "${RESULT_SERVICE}" \
  --project="${RESULT_PROJECT_ID}" \
  --region="${RESULT_REGION}" \
  --format='yaml(spec.template.spec.serviceAccountName,status.url)'
```

Set the returned service-account email:

```sh
export RESULT_RUNTIME_SA='<actual-runtime-service-account-email>'
```

If `serviceAccountName` is absent, first identify the project's default Cloud Run runtime identity; do not guess it. For the initial release, retaining the service's current identity is lower risk because it may already have access to existing provider secrets. A new dedicated identity is preferable long term, but only after every existing dependency is audited. See Google's [Cloud Run service identity guide](https://cloud.google.com/run/docs/securing/service-identity).

Do not set `GOOGLE_APPLICATION_CREDENTIALS` on Cloud Run and do not download a JSON service-account key. The Google client library uses the attached runtime identity automatically.

### 3. Create the private bucket

Create a regional Standard bucket next to the Cloud Run service:

```sh
gcloud storage buckets create "gs://${RESULT_BUCKET}" \
  --project="${RESULT_PROJECT_ID}" \
  --location="${RESULT_REGION}" \
  --default-storage-class=STANDARD \
  --uniform-bucket-level-access \
  --public-access-prevention \
  --soft-delete-duration=0
```

Why these settings:

- A regional bucket in `us-central1` avoids unnecessary cross-region latency and transfer.
- Standard storage has no minimum storage duration, which fits objects that live for only 3 or 7 days.
- Uniform bucket-level access keeps authorization in IAM instead of per-object ACLs.
- Public access prevention guards against accidentally making the result objects public.
- Soft delete is disabled because its default retention would preserve deleted objects and add cost beyond the intended result lifetime.

For an existing bucket, inspect its settings first. If soft delete is enabled, disable it with:

```sh
gcloud storage buckets update "gs://${RESULT_BUCKET}" --clear-soft-delete
```

Google references: [create a bucket with `gcloud`](https://cloud.google.com/sdk/gcloud/reference/storage/buckets/create), [uniform bucket-level access](https://cloud.google.com/storage/docs/using-uniform-bucket-level-access), [public access prevention](https://cloud.google.com/storage/docs/public-access-prevention), and [disable soft delete](https://cloud.google.com/storage/docs/disable-soft-delete).

### 4. Give AuraLens only object access

Grant the Cloud Run runtime identity object create/read/delete permission on this bucket:

```sh
gcloud storage buckets add-iam-policy-binding "gs://${RESULT_BUCKET}" \
  --member="serviceAccount:${RESULT_RUNTIME_SA}" \
  --role='roles/storage.objectUser'
```

Do not grant `allUsers`, `allAuthenticatedUsers`, Storage Admin, or project-wide storage access to the runtime identity. `roles/storage.objectUser` at this one bucket is sufficient for the startup access probe and normal result operations. See [Cloud Storage IAM roles](https://cloud.google.com/storage/docs/access-control/iam-roles) and [`buckets add-iam-policy-binding`](https://cloud.google.com/sdk/gcloud/reference/storage/buckets/add-iam-policy-binding).

### 5. Configure physical deletion

This backend PR includes `deploy/result-storage-lifecycle.json`. Apply it to the bucket:

```sh
gcloud storage buckets update "gs://${RESULT_BUCKET}" \
  --lifecycle-file='deploy/result-storage-lifecycle.json'
```

The rules delete 3-day result prefixes after 3 days, 7-day prefixes after 7 days, idempotency mappings after 7 days, and abandoned health-check probes after 1 day. Lifecycle execution is asynchronous, so objects can remain briefly after becoming eligible. This does not extend access: AuraLens checks the manifest timestamp on every metadata/media request and returns HTTP `410` as soon as the selected lifetime ends.

Verify the installed policy:

```sh
gcloud storage buckets describe "gs://${RESULT_BUCKET}" \
  --format='yaml(lifecycle_config,soft_delete_policy,iam_config)'
```

See [configure Object Lifecycle Management](https://cloud.google.com/storage/docs/managing-lifecycles) and [lifecycle timing and behavior](https://cloud.google.com/storage/docs/lifecycle).

### 6. Create and attach the developer API key

Create a cryptographically random key with at least 32 characters. The following creates a uniquely named temporary file that is readable only by the current local user:

```sh
umask 077
export RESULT_SECRET_FILE="$(mktemp)"
openssl rand -hex 32 > "${RESULT_SECRET_FILE}"
gcloud secrets create upscaler-tool-api-key \
  --replication-policy='automatic' \
  --project="${RESULT_PROJECT_ID}"
gcloud secrets versions add upscaler-tool-api-key \
  --data-file="${RESULT_SECRET_FILE}" \
  --project="${RESULT_PROJECT_ID}"
```

If the secret already exists, skip `gcloud secrets create` and add a new version. Grant only the runtime service account access:

```sh
gcloud secrets add-iam-policy-binding upscaler-tool-api-key \
  --member="serviceAccount:${RESULT_RUNTIME_SA}" \
  --role='roles/secretmanager.secretAccessor' \
  --project="${RESULT_PROJECT_ID}"
```

Note the version number printed by `gcloud secrets versions add`, then attach that numbered version to the service. A pinned version makes rollback behavior explicit:

```sh
export RESULT_TOOL_SECRET_VERSION='<version-number-just-created>'
gcloud run services update "${RESULT_SERVICE}" \
  --project="${RESULT_PROJECT_ID}" \
  --region="${RESULT_REGION}" \
  --update-secrets="UPSCALER_TOOL_API_KEY=upscaler-tool-api-key:${RESULT_TOOL_SECRET_VERSION}"
```

Copy the same value from `${RESULT_SECRET_FILE}` into each authorized developer's ignored `UpscaleWebsite/.env`, then delete the temporary file and unset the local variables:

```sh
rm "${RESULT_SECRET_FILE}"
unset RESULT_SECRET_FILE RESULT_TOOL_SECRET_VERSION
```

Never paste the value into a command argument, PR, issue, chat, build log, Cloudflare setting, or tracked file. The static website does not need this secret; only the local developer command does. See [create a Secret Manager secret](https://cloud.google.com/secret-manager/docs/creating-and-accessing-secrets), [grant access to a secret](https://cloud.google.com/secret-manager/docs/manage-access-to-secrets), and [use Secret Manager with Cloud Run](https://cloud.google.com/run/docs/configuring/services/secrets).

### 7. Configure non-secret Cloud Run settings

Update only the new variables so existing provider configuration is preserved:

```sh
gcloud run services update "${RESULT_SERVICE}" \
  --project="${RESULT_PROJECT_ID}" \
  --region="${RESULT_REGION}" \
  --update-env-vars="RESULTS_STORAGE_BACKEND=gcs,RESULTS_GCS_BUCKET=${RESULT_BUCKET},RESULTS_SITE_BASE_URL=https://upscales.app,RESULTS_ALLOWED_ORIGINS=https://upscales.app"
```

Use `--update-env-vars`, not `--set-env-vars`: the latter replaces previously configured values. Keep the existing `WAVESPEED_API_TOKEN`, `REPLICATE_API_TOKEN`, `AURALENS_SECRET`, and any other service configuration intact. Provider tokens should also be Secret Manager references, not literal environment values. See [configure Cloud Run environment variables](https://cloud.google.com/run/docs/configuring/services/environment-variables).

Optional upload validation limits are `RESULTS_MAX_IMAGE_BYTES` (40 MiB per image by default) and `RESULTS_MAX_IMAGE_PIXELS` (100 million pixels by default). Do not increase the byte limit until the request-size issue below is resolved.

### 8. Deploy and verify the backend

After the backend PR is merged, deploy it using the repository's existing release process (`./build_and_deploy.sh`). That script updates the image and preserves service configuration; the storage and secret commands above remain a separate one-time setup.

With `RESULTS_STORAGE_BACKEND=gcs`, a new AuraLens instance performs a create/read/delete probe under `_healthcheck/` at startup. A bad bucket name, missing Application Default Credentials, or insufficient IAM permission causes startup to fail instead of accepting jobs it cannot publish.

Verify the deployed revision and logs, then health:

```sh
gcloud run services describe "${RESULT_SERVICE}" \
  --project="${RESULT_PROJECT_ID}" \
  --region="${RESULT_REGION}" \
  --format='yaml(status.url,status.latestReadyRevisionName,spec.template.spec.serviceAccountName)'
gcloud run services logs read "${RESULT_SERVICE}" \
  --project="${RESULT_PROJECT_ID}" \
  --region="${RESULT_REGION}" \
  --limit=100
curl --fail --show-error \
  'https://auralens-406817559814.us-central1.run.app/healthz'
```

### 9. Deploy the website

After the backend is healthy, merge the website PR. The static build command is:

```sh
python3 build/build.py
```

The deployment output is `dist/`. Configure the existing Cloudflare Pages project to build that command and publish that directory, or let its Git integration deploy the merged branch. The checked-in `_redirects` rule maps `/results/<UUID>` to the single result-page application, and `_headers` supplies the result page's security policy. See [Cloudflare Pages build configuration](https://developers.cloudflare.com/pages/configuration/build-configuration/).

No API key or Google credential belongs in Cloudflare. The browser calls only AuraLens public read routes; the developer command runs locally and calls the protected routes itself.

### 10. Run the production smoke test

1. Confirm that `GET /internal/v1/tool-access` returns `401` without a bearer key and with a deliberately incorrect key, and `200` only with the intended developer key.
2. Run one Creative Upscale command with a small non-sensitive image and `--retention 3`. This is one real WaveSpeed call.
3. Open the printed URL and confirm before/after dragging, metadata, expiration copy, and download.
4. Run one Photo Restoration command with a small non-sensitive image. This is one real Replicate call.
5. Confirm the bucket contains `before`, `after`, and `manifest.json` below the matching UUID prefix, but anonymous storage URLs cannot read them.
6. Check Cloud Run errors, provider charges, request latency, and bucket object count after the test.

The startup probe tests bucket connectivity without a paid model call. Run paid smoke tests only after that probe and the public page are healthy.

## Known production issues and follow-up work

### Combined upload size

`POST /internal/v1/results` currently sends both images in one multipart request through Cloud Run. The application permits up to 40 MiB per image, but Cloud Run's maximum HTTP/1 request size is 32 MiB. Two allowed images can therefore exceed the platform limit before the request reaches FastAPI. Large 8K results, especially PNGs, are the likely failure case. See [Cloud Run quotas and limits](https://cloud.google.com/run/quotas).

For the initial internal release, keep the combined before/after payload below roughly 30 MiB and prefer JPEG or WebP output. Do not treat the current 40 MiB per-file application limit as a guarantee that Cloud Run will accept the pair.

The scalable fix is a three-step upload design:

1. The authenticated command asks AuraLens to create a result UUID and short-lived resumable or signed upload targets.
2. The command uploads `before` and `after` directly to the private bucket, avoiding Cloud Run's request body and memory limits.
3. The command asks AuraLens to validate the objects and finalize the manifest before returning the result URL.

That change should include upload expiry, content-length and content-type restrictions, checksum validation, cleanup for abandoned uploads, and idempotent finalization. Direct browser upload is not needed because this remains developer tooling.

### Signed media delivery

Before result volume grows, replace backend byte streaming with short-lived signed `GET` URLs as described above. Keep the metadata endpoint and its expiry check: it is the authority that decides whether a result may receive fresh media URLs. Cap every signed URL expiry at `min(now + short window, manifest expires_at)` so a URL is never intentionally valid beyond the selected result lifetime.

This requires a narrow signing permission for the Cloud Run runtime identity, tests for URL expiry and response metadata, and frontend handling for a refreshed metadata response. Do not make the bucket public as a shortcut.

### Deletion and retention

Logical access expiry is already enforced by AuraLens at the exact manifest timestamp. Physical deletion still depends on the lifecycle policy being applied to the production bucket. Lifecycle deletion is asynchronous, and enabled soft delete or bucket retention policies can preserve data longer and add storage cost.

Before release:

- apply `deploy/result-storage-lifecycle.json`;
- verify soft delete is disabled and no conflicting retention policy is configured;
- confirm the lifecycle rules target `results/3d/`, `results/7d/`, `idempotency/`, and `_healthcheck/`;
- use a test bucket with shorter test-only rules to verify actual deletion behavior, because production rules take days;
- monitor bucket bytes/object count and periodically audit objects older than their expected lifecycle window.

If regulatory deletion timing ever becomes strict, add a scheduled deletion job rather than relying only on asynchronous lifecycle evaluation.

### Operational hardening

Before expanding beyond a few trusted developers:

- add per-key rate limits or quotas to the internal provider routes;
- configure provider budgets/alerts and Google Cloud billing budgets ([Google Cloud budget alerts](https://cloud.google.com/billing/docs/how-to/budgets));
- alert on Cloud Run `5xx`, provider `502`, result-publish failures, latency, and bucket growth;
- define a key owner and rotation/revocation procedure;
- implement short-lived signed media URLs before streaming full images through Cloud Run becomes a material cost, latency, or memory problem; consider a CDN only after measuring signed-URL delivery.

## Troubleshooting

- `401 Invalid tool API key`: the command key is missing, wrong, or different from the Cloud Run secret version.
- `503 Tool API is not configured`: the server key is missing or shorter than 32 characters.
- Cloud Run revision never becomes ready with GCS enabled: verify `RESULTS_GCS_BUCKET`, the runtime service account, and its bucket-level `roles/storage.objectUser` grant.
- `503 Result storage is not configured`: storage is disabled or was not initialized correctly.
- `404 Result not found`: the UUID is unknown or lifecycle deletion has already removed its manifest.
- `410 This result has expired`: the selected 3- or 7-day logical lifetime has elapsed.
- `413` or a Cloud Run request-size failure during publish: reduce/compress the pair and prioritize the direct-to-bucket upload follow-up.
